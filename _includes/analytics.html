{%- comment -%} Google Analytics 4 (gtag.js). HISTORY — read before editing, this replaced something load-bearing. Until now this site carried a hardcoded gtag.js tag for UA-147627714-1, a Universal Analytics property. The UA property itself is long gone (Google stopped processing UA data on 1 July 2023 and deleted the properties in 2024), but that tag was NOT dead. Google's UA-to-GA4 migration wired the on-page UA tag to an auto-created GA4 property through the "connected site tags" mechanism, and Google kept a snapshot of that configuration working after the UA properties were deleted. Fetching https://www.googletagmanager.com/gtag/js?id=UA-147627714-1 still returns a container that loads a child container for G-4261TQJZV6 — that indirection is what has been feeding the dashboard. So the UA tag was collecting, and deleting it without a replacement would have silently ended data collection. It has been swapped for a direct GA4 tag pointing at the SAME property, G-4261TQJZV6, which is what Google recommends: a native tag restores the full Google-tag feature set that connected site tags cannot support, and removes a redundant network hop. The swap had to be atomic. A native GA4 tag for G-4261TQJZV6 sitting on the page alongside the old UA tag would have sent two pageviews per view into one property, corrupting the history going forward. Never reintroduce the UA block while this include is active. The measurement ID comes from `google_analytics` in _config.yml, and is deliberately the same value used by byu-adept-lab.github.io: one property, one web data stream, both sites tagged identically. The nav here links straight to the lab site, so visitors cross hostnames mid-session, and GA4 only stitches a session across domains when both carry the same tag. The two sites stay separable in reports via the `hostname` dimension. Both sites are *.github.io, and github.io is on the Public Suffix List, so no cookie can be set at the shared parent and each hostname has its own cookie jar. Cross-domain stitching must therefore be enabled explicitly in the GA4 admin; it does not happen implicitly just because both hosts end in github.io. Two guards, both necessary: - jekyll.environment must be "production", so local previews never report into real data. GitHub Pages satisfies this on its own: branch-based deploys run GitHub's managed pages-build-deployment workflow, which builds via actions/jekyll-build-pages, and that action exports JEKYLL_ENV=production. Note this is stricter than the old UA tag, which fired on localhost too and was quietly polluting the data. - the ID's stripped length must be non-zero. There is no String#blank? in this Liquid stack, so an "x != blank" comparison silently evaluates true for an empty string and would emit a broken gtag('config', '') — which is exactly the bug the previous analytics.js version of this file had, since it read an empty config key. Piping through strip and size is the test that actually holds. (Note for future editors: do not write literal Liquid block-tag syntax inside a comment block like this one. Liquid still parses block tags in here, so an unbalanced if- or comment-tag written as prose will break the build.
